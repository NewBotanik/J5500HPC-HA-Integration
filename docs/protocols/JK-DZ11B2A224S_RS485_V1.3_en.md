# JK-DZ11-B2A24S Balancer Communication Protocol V1.3

> English translation of the vendor document `JK-DZ11B2A224S_RS485_V1.3.pdf`
> (original language: Chinese). The structure, section numbering and example
> data follow the original. Translator notes are marked with **[TN]**; they
> point out inconsistencies of the original and are not part of the vendor
> text. This protocol applies to the **RS485** port only; over Bluetooth the
> device uses the JK02 protocol of JK BMS devices. See
> [jikong_active_balancer.md](jikong_active_balancer.md) for both.

## 1. Overview

This protocol defines the electrical interface, data format, communication
rate, etc. of the external communication of the JK-DZ11-B2A24S balancer board.

## 2. Communication parameters

The communication parameters are given in Table 1.

**Table 1**

| Parameter | Value |
|---|---|
| Communication interface | RS485 |
| Baud rate | 9600 |

> **[TN]** Data bits, parity and stop bits are not specified in the original;
> 8N1 is the common default and works with a real JK-DZ11-B2A24S. If the A/B
> wires are swapped, the device returns only a short `55 95 01 FF 01` instead
> of the 74-byte reply.

## 3. Communication format

The system communicates using a master/slave request-response scheme. During
communication the balancer is the slave and the controlling device is the
master. All communication can only be initiated by the master; after receiving
a command, the slave performs the corresponding operation and returns the
result to the master within 1 s. If no complete response frame is received
from the slave within 1 s, the transmission is considered failed. After
sending a frame, the master must wait for the slave's reply or for the timeout
before it may send the next command.

The communication content is expressed in hexadecimal and transmitted in units
of "frames". Data transferred from the master to the slave is called
*downlink*; data transferred from the slave to the master is called *uplink*.

### 4.3 Master downlink frame format

> **[TN]** The section numbers 4.3 and 4.4 appear here in the original before
> section 4; they are kept as-is.

A downlink frame sent by the master consists of 5 fields: frame header, slave
address, command code, frame data and checksum. The frame format is shown in
Table 2.

**Table 2 – Downlink frame format**

| Frame header | Slave address | Command code | Frame data | Checksum |
|---|---|---|---|---|
| 2 Byte | 1 Byte | 1 Byte | 2 Byte | 1 Byte |

Where:

- "Frame header" marks the start of a frame; length 2 bytes, fixed to
  `0x55 0xAA`;
- "Slave address" is the number of the slave addressed by this command; length
  1 byte;
- "Command" is the operation of this frame;
- "Frame data" is the data carried by this frame;
- "Checksum" is an additive checksum: the sum of all bytes from the frame
  header through the frame data.

> **[TN]** The checksum is the lower 8 bits of the sum; all examples in this
> document verify with `sum(frame[0:-1]) & 0xFF`.

### 4.4 Slave uplink frame format

An uplink frame sent by the slave consists of 6 fields: frame header, slave
address, command code, frame data, checksum.

> **[TN]** The original says "6 fields" but lists (and the table shows) 5.

**Table 3 – Uplink frame format**

| Frame header | Slave address | Command code | Frame data | Checksum |
|---|---|---|---|---|
| 2 Byte | 1 Byte | 1 Byte | 69 Byte | 1 Byte |

Where:

- "Frame header" marks the start of a frame; length 2 bytes, fixed to
  `0xEB 0x90`;
- "Slave address" is the number of the slave addressed by this command; length
  1 byte;
- "Command" is the downlink command this frame responds to;
- "Frame data" is the data carried by this frame;
- "Checksum" is an additive checksum: the sum of all bytes from the frame
  header through the frame data.

> **[TN]** Total uplink frame length is therefore 2 + 1 + 1 + 69 + 1 =
> **74 bytes**.

## 4. Communication flow

The following description uses device address `0x01` as an example.

### 4.1 Request balancer data

1) Master sends:

```
55 AA 01 FF 00 00 FF
```

The data structure is shown in Table 4.

**Table 4**

| Offset | Content | Data type | Length | Unit | Example data |
|---|---|---|---|---|---|
| 0 | Frame header | UINT8 | 2 | - | 0x55 0xAA |
| 2 | Slave address | UINT8 | 1 | - | 0x01 |
| 3 | Command code | UINT8 | 1 | - | 0xFF |
| 4 | Frame data | UINT16 | 1 | - | 0x0000 |
| 6 | Checksum | UINT8 | 1 | - | 0xFF |

> **[TN]** In all tables the "Length" column is the number of elements of the
> given data type, not the number of bytes (e.g. `UINT16 × 1` = 2 bytes).

2) Balancer response:

```
EB 90 01 FF 1E D3 0F 69 14 13 02 00 00 00 07 00 00 00 05 03 E8 01 14 0F 69 0F 69
0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F
69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 0F 69 00 16 6F
```

> configured; all 24 slots are filled with `0F 69` in the example.
>
> **[TN] Measured on a real JK-DZ11-B2A24S (16 cells, 2 A model), compared with
> the JK app** ([jikong_active_balancer.md](jikong_active_balancer.md#checked-on-a-real-device-2026-10-09)):
>
> - Offsets 9 and 10 are **0-based cell indices**: 0 and 15 for cells 1 and 16
>   (the example's "cell 19" / "cell 2" is the raw value).
> - Offset 71 is the temperature in **0.1 °C**, not °C: `00 BE` = 190 while
>   the app shows 18.9 °C (so the example `00 16` would be 2.2 °C).
> - Offset 12, BIT0 ("cell-count setting error") is **set on a healthy
>   device** with 16 configured and 16 detected cells and no alarm in the app;
>   its real meaning is unknown.
> - Offset 19 reports **2000 mA** on the 2 A model, above the range in
>   Note 2 of §4.4.
> - Cell connection (balance lead) resistances, shown in the app, are **not**
>   part of this protocol; the device sends them only over Bluetooth (JK02).

### 4.2 Set number of cells in series

1) Master sends:

```
55 AA 01 F0 00 10 00
```

The data structure is shown in Table 6.

**Table 6**

| Offset | Content | Data type | Length | Unit | Example data |
|---|---|---|---|---|---|
| 0 | Frame header | UINT8 | 2 | - | 0x55 0xAA |
| 2 | Slave address | UINT8 | 1 | - | 0x01 |
| 3 | Command code | UINT8 | 1 | - | 0xF0 |

| 6 | Checksum | UINT8 | 1 | - | 0x00 |
