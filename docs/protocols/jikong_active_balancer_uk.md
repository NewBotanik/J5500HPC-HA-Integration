# Активний балансир Jikong (JK) JK-DZ11-B2A24S

Нотатки щодо автономної плати активного балансира Jikong `JK-DZ11-B2A24S`
(2–24 послідовні комірки). Пристрій має два незалежні інтерфейси з **різними
протоколами**:

| Інтерфейс | Протокол | Використовується в aiobmsble |
|---|---|---|
| Bluetooth LE | JK02 (протокол застосунку JK BMS, кадри `55 AA EB 90`, структура JK02_32S) | Так, через `aiobmsble/bms/jikong_bms.py` (варіант для балансира) |
| RS485 | Протокол балансира виробника V1.3 (запит `55 AA` / відповідь `EB 90` на 74 байти) | Ні |

**Окремого плагіна** для цього пристрою немає. По BLE він поводиться як JK BMS,
а його оголошення неможливо відрізнити від оголошення JK BMS (див.
[Ідентифікація по BLE](#ідентифікація-по-ble)). `jikong_bms.py` розпізнає
балансир за рядком моделі в кадрі інформації про пристрій `0x03` і переходить
на скорочений набір полів (див. [Підтримка в aiobmsble](#підтримка-в-aiobmsble)).

Англійська версія: [jikong_active_balancer.md](jikong_active_balancer.md).

## Ідентифікація по BLE

Записане оголошення (збережене в `aiobmsble/test_data/jikong_bms.json`):

| Параметр | Значення |
|---|---|
| Локальне ім'я | `50301130603` (ім'я пристрою задає користувач; за замовчуванням дорівнює серійному номеру) |
| MAC-адреса | `C8:47:80:31:F6:43` |
| ID виробника | `0x0B65` (2917), дані `88 a0 c8 47 80 31 f6 43` = `88 a0` + MAC |
| UUID сервісів | `0xFFE0`, `0xFEE7` |

Це той самий шаблон, що й у пристроїв JK BMS, і `jikong_bms.py` його
розпізнає (`service_uuid=0xFFE0`, `manufacturer_id=0x0B65`). В оголошенні
немає нічого, що вказувало б на балансир: локальне ім'я задає користувач, а
дані виробника — це просто MAC-адреса. Тому окремий плагін балансира порушив
би правило унікальності матчерів (`tests/test_plugins.py::
test_advertisements_unique`).

|---|---|---|---|

## Протокол BLE (JK02)

Формат кадрів, контрольна сума й команди — це протокол JK BMS, реалізований у
`jikong_bms.py`:

- Команда: `aa 55 90 eb` + байт команди + довжина + 13 байтів даних + 8-бітна
  сума (20 байтів).
- Відповідь: `55 aa eb 90` + тип кадру (зміщення 4) + лічильник кадрів
  (зміщення 5) + дані, 300 байтів; останній байт — 8-бітна сума байтів 0…298.
  Відповіді надходять 4 сповіщеннями (128 + 22 + 128 + 22 байти).
- Прошивка `11.55` → структура JK02_32S (зміщення протоколу 0 у
  `jikong_bms.py`).

### Записаний обмін

```text
TX  aa 55 90 eb 97 00 … 00 11     # запит інформації про пристрій
RX  55 aa eb 90 03 …  (300 Б)     # 0x03 інформація про пристрій
RX  aa 55 90 eb c8 01 01 00 … 44  # 0xC8 «готовий», окреме сповіщення
TX  aa 55 90 eb 96 00 … 00 10     # запит даних комірок
RX  55 aa eb 90 01 …  (300 Б)     # 0x01 налаштування
RX  55 aa eb 90 03 …  (300 Б)     # 0x03 інформація про пристрій (повтор)
RX  aa 55 90 eb c8 …              # 0xC8 (повтор)
RX  55 aa eb 90 02 …  (300 Б)     # 0x02 дані комірок, далі потоком приблизно кожні 0,55 с
```

Після `0x96` пристрій спершу надсилає `0x01` і `0x03`, а потім, поки
з'єднання активне, безперервно передає кадри `0x02`. `jikong_bms.py` ігнорує
неочікувані типи й використовує останній кадр `0x02`. Неповні кадри через
втрачені сповіщення (150/172/278 байтів у логах) не проходять перевірку
контрольної суми й відкидаються.

## Підтримка в aiobmsble

`jikong_bms.py` встановлює `_balancer`, коли модель починається з `JK_DZ`
(`_BALANCER_MODELS`). Для балансира він:

- окрім даних комірок, декодує лише `voltage`, `problem_code`,
  `balance_current` і `balancer` (`_FIELDS_BALANCER`), тож завжди нульові
  `current`, `battery_level`, `cycle_charge`, `cycles`, `battery_health`,
  стани MOSFET і налаштування ємності не повідомляються;
- читає температуру лише зі зміщення 162 (`_TEMP_POS_BALANCER`) і ігнорує
  хибну маску датчиків на зміщенні 214.

Для всіх пристроїв JK (BMS і балансира) опори підключення комірок
повідомляються як `cell_resistances` (в Ом, по одному значенню на кожну
увімкнену комірку, читаються зі зміщення 80, або 64 для структури JK02_24S).
Це опір балансувального проводу та його клем, виміряний пристроєм, а не
внутрішній опір комірки. Найімовірніше, саме ці опори показує застосунок
виробника (значення ще не звірено поштучно).

До цієї зміни логи показували `problem: True` (через `cycle_charge = 0`),
три фіктивні датчики з 0 °C і усереднену температуру 2,9 °C. Тепер для
тестового кадру варіант балансира дає:

```python
{
    "voltage": 53.175,
    "problem_code": 0,
    "balance_current": 0.0,
    "balancer": False,
    "cell_count": 16,
    "delta_voltage": 0.002,
    "cell_voltages": [3.323] * 11 + [3.325] + [3.323] * 4,
    "cell_resistances": [0.065, 0.072, 0.071, 0.068, 0.075, 0.071, 0.073, 0.071,
                         0.065, 0.141, 0.127, 0.073, 0.071, 0.072, 0.069, 0.065],
    "temp_values": [TempSensor(11.6)],
    "temperature": 11.6,
    "problem": False,
}
```

Тести: `tests/bms/test_jikong_bms.py::test_balancer_update`,
`test_balancer_device_info`, `test_balancer_active`.

### Обмеження, що залишаються

- Кадру з активним балансуванням ще не записано; знак і масштаб
  `balance_current` під час балансування варто підтвердити логом, знятим тоді,
  коли різниця напруг комірок перевищує поріг.
- Проблеми зі з'єднанням в issue (`BleakOutOfConnectionSlotsError`)
  спричинені налаштуванням Bluetooth у Home Assistant, а не протоколом.

## Протокол RS485 (довідково)

Стислий виклад документа виробника для дротового підключення (наприклад,
через RS485-адаптер). По BLE він **не** використовується. Подробиці та
оригінальні приклади кадрів — у перекладах, посилання на які наведено вище;
контрольні суми всіх прикладів перевірено.

### Модель обміну

- Ведучий/ведений, запит-відповідь; балансир ніколи не надсилає дані без
  запиту.
- 9600 бод (формат байта не вказано; припускається 8N1).
- Відповідь протягом 1 с; наступний запит — лише після відповіді або
  тайм-ауту.
- Запит — 7 байтів, кожна відповідь — 74 байти.
- Багатобайтові значення — беззнакові big-endian, якщо не зазначено інше.

### Кадри

```text
запит:     [55 AA] [ADDR] [CMD] [DATA_HI DATA_LO] [CHK]          7 байтів
відповідь: [EB 90] [ADDR] [CMD] [DATA × 69]       [CHK]         74 байти
CHK = sum(усі попередні байти, включно із заголовком) & 0xFF
```

### Команди

| Cmd | Призначення | Дані запиту (u16) | Діапазон | Відповідь |
|---|---|---|---|---|
| `0xFF` | Стан і напруги комірок | `0x0000` | – | Див. таблицю нижче |
| `0xF0` | Кількість комірок | шт. | 2–24 | Активне значення на зміщенні 4, решта `00` |
| `0xF2` | Різниця напруг запуску балансування | мВ | 2–1000 | Активне значення на зміщенні 4, решта `00` |
| `0xF4` | Макс. струм балансування | мА | 30–1000 | Активне значення на зміщенні 4, решта `00` |
| `0xF6` | Балансування увімк./вимк. | 0/1 | 0–1 | Активне значення на зміщенні 4, решта `00` |

Значення поза діапазоном ігноруються, а відповідь містить поточне активне
значення.
